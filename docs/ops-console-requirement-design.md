# 绿云运维控制台需求与设计草案

## 1. 背景与目标

本项目计划建设一个统一的运维管理平台，名称暂定为“绿云运维控制台”。平台用于集中管理多个项目的运维入口，用户登录后只能看到并进入自己被授权的项目模块；管理员可以维护用户、项目模块和项目内功能树。

当前阶段目标是先搭出可扩展骨架，不急于实现具体业务工具功能，重点先确认用户体系、权限体系、项目配置能力和 UI 风格。

## 2. 用户与权限需求

### 2.1 用户类型

- 管理员用户：默认账号为 `admin`，拥有全部权限。
- 永久用户：由管理员创建，长期可用，可分配一个或多个项目模块权限。
- 临时用户：由管理员一键创建，有效期通过参数配置；临时用户同样可以分配一个或多个项目模块权限。

### 2.2 管理员能力

- 创建、编辑、启用、禁用永久用户。
- 一键创建临时用户，并设置或自动生成过期时间。
- 区分查看永久用户和临时用户。
- 给用户分配可访问的项目模块。第一期采用“用户直接授权项目”，不引入角色体系。
- 新增、编辑、禁用项目模块。
- 给项目模块配置内部功能树。

### 2.3 普通用户能力

- 登录系统。
- 只能看到自己有权限访问的项目模块。
- 进入项目模块后，看到该项目下已启用的功能树节点。第一期不做项目内功能节点权限控制。

## 3. 项目模块设计

当前先预置 3 个项目模块：

- 用户管理：仅 `admin` 可见，用于管理用户、临时用户、权限分配、项目模块和功能树配置。
- mihotel：运维项目模块。
- ihotel：运维项目模块。

项目模块必须可配置，不写死在前端代码里。后续管理员应能新增类似 `pms-toolkit`、`group`、`thef` 等项目模块，并配置名称、编码、图标、描述、排序、启用状态。

## 4. 功能树设计

每个项目模块内部使用树形功能列表，参考第三张图的侧边栏体验。功能树应支持多级结构，便于后续扩展。第一期功能树只负责菜单和入口配置，不控制用户权限。

功能节点建议包含：

- 节点名称：例如“酒店查询”“Git 版本管理”。
- 节点编码：用于权限判断和路由定位。
- 节点类型：目录、菜单、按钮或外部链接。
- 路由地址或外部链接。
- 是否预留单点登录。
- 父节点。
- 排序号。
- 启用状态。
- 是否需要权限控制。

当前 `mihotel` 和 `ihotel` 可以先配置示例功能树，不急于实现每个功能的真实业务逻辑。

## 5. 页面规划

### 5.1 登录页

参考第一张图，但替换为本系统信息：

- 系统名：绿云运维控制台。
- 左侧深色品牌区：展示平台名称、定位说明、核心卖点。
- 右侧登录卡片：用户名、密码、登录按钮。
- 登录后根据用户权限进入项目模块列表页。

### 5.2 项目模块列表页

参考第二张图的功能，但 UI 风格要统一到第一张和第三张图：

- 顶部或左侧展示当前登录用户、退出登录。
- 主区域以卡片方式展示可访问项目模块。
- 普通用户只展示有权限项目。
- `admin` 额外看到“用户管理”和“新增项目模块”等入口。
- 卡片信息包含项目名称、描述、状态、入口按钮。

### 5.3 用户管理页

仅 `admin` 可访问，建议包含：

- 用户列表：区分永久用户和临时用户。
- 新增永久用户。
- 一键新增临时用户。
- 启用、禁用、重置密码。
- 分配项目模块权限。
- 查看临时用户过期时间。

### 5.4 项目配置页

仅 `admin` 可访问，建议包含：

- 项目模块列表。
- 新增、编辑、禁用项目模块。
- 配置项目模块可见用户。
- 进入功能树配置。

### 5.5 功能树配置页

仅 `admin` 可访问，建议包含：

- 左侧树形功能节点。
- 右侧节点表单。
- 新增同级节点、新增子节点、编辑、禁用、排序。
- 支持目录、菜单、按钮、外部链接等节点类型。

### 5.6 项目运维页

进入 `mihotel` 或 `ihotel` 后使用第三张图类似布局：

- 左侧深色项目侧栏。
- 顶部浅色标题栏。
- 中间为当前功能内容区。
- 功能列表来自后台配置的树形节点。

## 6. UI 风格方向

第一张图和第三张图更接近，建议作为统一视觉方向：

- 深色品牌区或侧边栏：用于承载系统识别、项目名称、主导航。
- 浅色主工作区：用于表单、卡片、列表和配置操作。
- 卡片使用克制圆角，不做过度装饰。
- 色彩以深蓝黑、白色、浅灰、蓝色操作按钮为主，可少量使用绿色强化“绿云”品牌。
- 第二张图的蓝色顶栏和卡片布局可保留信息结构，但视觉上要改成第一张/第三张的统一风格。
- 后续所有页面保持同一套布局、按钮、输入框、卡片、侧栏和状态标签规范。

## 7. 建议数据模型草案

后续建表脚本应放入 `database/` 目录。初步建议表：

- `sys_user`：用户基础信息。
- `ops_project`：项目模块配置。
- `ops_user_project_permission`：用户与项目模块的授权关系。
- `ops_function_node`：项目内功能树节点。
- `sys_login_log`：登录日志。
- `sys_operation_log`：关键管理操作日志。

第一期暂不引入角色表和功能节点授权表，避免权限模型过重。后续如果用户量、项目量和权限组合复杂度上升，再补角色体系。

## 8. 初步权限规则

- `admin` 默认拥有全部项目模块和全部功能节点权限。
- 用户登录时加载可访问项目模块。
- 进入项目模块时校验项目权限。
- 加载项目功能树时返回该项目已启用节点，不做用户级节点权限过滤。
- 临时用户登录时必须校验过期时间。
- 禁用用户、禁用项目、禁用功能节点后应立即不可访问。

## 9. 可能遗漏或需要确认的问题

1. 临时用户到期后是保留记录、自动禁用，还是定期清理？
2. 用户密码是否需要强度规则、首次登录改密、重置密码能力？
3. 是否需要 IP 白名单等更强安全策略？
4. 外部链接和 SSO 的具体跳转参数、签名方式后续需要确认。
5. 是否需要项目收藏、最近访问、常用功能置顶？
6. `mihotel` 和 `ihotel` 第一批具体功能清单还未确认。

## 10. 第一阶段建议范围

第一阶段建议先实现：

- 登录页 UI。
- 模拟或基础后端登录。
- 项目模块列表页。
- `admin` 用户管理页骨架。
- 项目模块配置页骨架。
- 功能树配置页骨架。
- `mihotel`、`ihotel` 运维页骨架。
- 数据库表结构设计与初始化 `admin` 用户脚本。

具体业务工具能力可以放到第二阶段逐步补。
